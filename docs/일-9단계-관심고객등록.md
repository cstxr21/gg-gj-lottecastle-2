# 관심고객등록 — Supabase + Telegram 연동

> 🔑 **이 문서는 실값(키·토큰) 기재 문서다 — 로컬 전용**. 따라서 **git 커밋·현장 레포 복사 절대 금지**: 신규 현장에 docs를 복붙할 때 **이 9단계 파일은 제외하거나 §1 키 줄을 지우고 복사**하고, 현장 레포에는 `.env.local`로만 옮긴다(`.env*` gitignore 확인). Supabase URL·anon key는 원래 브라우저에 노출되는 공개값(RLS가 보호)이라 위험도 낮지만, **`TELEGRAM_BOT_TOKEN`은 진짜 비밀값** — 유출되면 봇 탈취·알림방 스팸이 가능하므로, 유출 의심 시 BotFather `/revoke`로 즉시 재발급(2분). ※재발급 시 이 값을 쓰는 **민간임대·지주택 9단계 문서(민-9단계·지-9단계-관심고객등록.md)·전 현장 호스팅 환경변수도 함께 갱신**(같은 봇 공유).
> 흐름: 폼 제출 → ① Supabase `inquiries` 저장 → ② 텔레그램 알림. **모든 현장이 하나의 `inquiries` 테이블을 공유**하고 `site` 컬럼으로 구분.

## 2. Supabase 테이블 (프로젝트 **최초 1회만**)

> ⚠️ 이 SQL은 프로젝트를 **처음 만들 때 1회**만. 이미 다른 현장이 쓰는 **공유 프로젝트엔 실행하지 않는다**(테이블·정책 이미 존재 → 재실행 시 에러). 새 현장은 §3만 따른다.

```sql
create table public.inquiries (
  id             bigint generated always as identity primary key,
  created_at     timestamptz not null default now(),   -- 접수 시각(자동)
  site           text not null,              -- 현장 식별자 (예: 'seoul-oo')
  name           text not null,
  phone          text not null,
  preferred_time text,                       -- 연락 가능한 시간대
  agreed         boolean not null default false,        -- 개인정보 동의
  source         text,                       -- 유입 페이지(referer)
  user_agent     text                        -- 접속 환경
);
create index on public.inquiries (site, created_at desc);

-- RLS: 폼 접수(INSERT)만 허용, 조회 차단(개인정보 보호)
alter table public.inquiries enable row level security;
create policy "anon insert inquiries" on public.inquiries
  for insert to anon with check (true);

comment on table public.inquiries is '관심고객등록 (다현장 공유 · site 컬럼으로 구분)';
```

---

## 3. 새 현장 추가 (DB 작업 없음)

> ✅ 테이블·RLS 정책은 공유 프로젝트에 **이미 있다.** 같은 URL·anon 키만 넣으면 그 현장 `site` 값으로 insert가 그대로 된다. SQL Editor 열 일 없음.

1. **코드 복사**(그대로): `src/lib/supabase.ts` · `src/app/api/contact/route.ts` · 폼 컴포넌트
2. **`src/lib/site.ts`** — 현장 값 교체. `inquiries.site`에 저장될 식별자(영문-하이픈, 고유)는 그 레포 site.ts의 정의 필드를 따른다(`key`/`slug` 등).
3. **`.env.local`** — §1 복사용 블록 **4줄 그대로**(`TELEGRAM_CHAT_ID` 포함 전 현장 동일).
4. **설치·재시작**: `npm install @supabase/supabase-js` 후 `npm run dev`(.env.local은 서버 시작 시 로드 → 재시작 필수).
5. ⚠️ **배포 시 호스팅 환경변수 등록(누락 = 배포 후 폼 503)**: `.env.local`은 **로컬 전용**이라 배포 서버엔 안 올라간다. 배포 전에 호스팅(Vercel 등) 대시보드 → Environment Variables에 **같은 4개를 등록**(4개 모두 그대로, CHAT_ID 포함) 후 재배포. 로컬은 되는데 배포만 503이면 100% 이 누락.

→ 끝. 폼 제출 시 같은 `inquiries`에 그 현장 `site` 값으로 쌓이고, 텔레그램엔 현장명이 찍힘.

## 4. 조회 (Supabase SQL Editor / Table Editor)

```sql
-- 특정 현장 최근 접수
select created_at, name, phone, preferred_time, source
from public.inquiries
where site = '<현장 site 값>'
order by created_at desc;

-- 현장별 접수 건수
select site, count(*) from public.inquiries group by site order by count desc;
```

> 웹(anon)은 RLS로 조회 불가(INSERT만). 관리자는 대시보드/Service Role로만 조회.

## 5. 동작 요약 (`route.ts`)

1. 검증: 성함 · 연락처(`01x-xxxx-xxxx`) · 동의 필수
2. `inquiries` insert (현장 `site` 값 포함)
3. **즉시 응답** — Supabase 저장 결과 기준(텔레그램 왕복 대기 X). 성공 `ok` / 실패 `502` / 전송 설정 미비 `503`.
4. 텔레그램은 응답 직후 **백그라운드(`after()`)** 발송(대기시간 미포함, 실패는 서버 로그):
   ```
   🏠 {site.name} 관심고객등록
   👤 성함: 홍길동
   📞 연락처: 010-1234-5678
   🕐 연락 가능 시간: 오후 12–15시
   ```

> **중복 발송 방지**(폼 컴포넌트): 제출 시 `submittingRef`(동기 가드)로 즉시 잠그고 버튼 `disabled`("전송 중…") → 더블클릭·연타 2중 접수 차단.

## 6. 트러블슈팅 — 흔한 오진

- **anon insert가 한 번 `42501`(RLS)로 막혀 보여도 "정책이 없다"고 단정하지 말 것.** 공유 프로젝트엔 정책이 이미 있다. 한 번 실패로 "SQL 돌려라"고 떠넘기는 건 오진이기 쉽다.
- 결론 전 **조건을 바꿔 재현**: ① 최소 페이로드(`site`·`name`·`phone`·`agreed`), ② 기존 현장 `site` 값, ③ 새 현장 `site` 값.
- **"다른 현장은 잘 된다" = DB가 아니라 코드/진단을 먼저 의심하라는 신호.**
- 새 현장에서 DDL(`create table`/`create policy`)을 **다시 돌리지 않는다**.
- `503`이 뜨면 정책이 아니라 환경변수 누락을 의심 — 로컬이면 `.env.local`, **배포 사이트면 호스팅 환경변수 미등록(§3-5)이 원인의 100%**.
